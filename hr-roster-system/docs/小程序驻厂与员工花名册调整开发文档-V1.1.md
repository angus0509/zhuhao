# 优益数字化管理系统——小程序驻厂与员工花名册调整开发文档 V1.1

> 文档版本：V1.1  
> 编制日期：2026-08-12  
> 适用项目：`/Users/zhuhao/Documents/moluo/hr-roster-system`  
> 技术栈：微信小程序 + 原生 Web + Node.js/Express + MySQL  
> 文档用途：直接用于开发、测试、部署和业务验收

## 1. 需求概述

本轮调整围绕“驻厂人员使用简单、员工状态流转清楚、敏感信息可控查看、网页花名册保持干净”四个目标实施。

核心调整：

1. 小程序底部菜单恢复为原五项菜单样式，取消点击瞬间变色、缩放和闪烁，并解决重复请求造成的点击延迟。
2. “驻厂管理”标题、页面头部和菜单名称统一对齐。
3. 工作台与驻厂管理共用同一套客户、人员状态和待办数据，所有统计均可进入对应员工列表。
4. 员工身份证号、银行卡号支持授权查看完整内容；默认仍脱敏，完整查看必须校验权限并留痕。
5. 在职员工支持一键办理离职；办结后退出在职花名册、关闭当前任职、失效员工账号并同步进入人才库。
6. 网页端员工花名册只显示正常在职员工；驻厂端只显示当前账号授权客户/项目内的员工。

### 1.1 本轮设计原则

- 不新建第二套员工状态字段，继续使用现有 `employee_status` 和 `lifecycle_status`。
- 不删除离职员工档案，离职员工通过人才库和员工历史档案查询。
- 数据隔离必须由后端 SQL 强制执行，不能只依靠前端隐藏。
- 身份证号、银行卡号不允许在员工列表中批量明文展示。
- 一键离职必须使用数据库事务，任何一步失败全部回滚。
- 页面跳转应先响应，再按需加载数据，不在点击事件中串行等待无关接口。

## 2. 用户角色与权限

| 角色 | 页面范围 | 员工数据范围 | 敏感信息 | 离职权限 |
|---|---|---|---|---|
| 企业管理员 | Web、小程序全部管理页面 | 本企业全部数据 | 默认可授权查看 | 可办理全部员工离职 |
| HR 主管 | Web、小程序 HR 页面 | 本部门及授权范围 | 默认可授权查看 | 可办理权限范围内员工离职 |
| 驻厂专员 | 小程序工作台、驻厂管理 | 仅授权客户/项目 | 仅在拥有 `employee:sensitive:view` 时可查看完整内容 | 可办理授权项目员工离职 |
| 薪资专员 | 工资、预支相关页面 | 授权范围 | 默认不可查看完整身份证号 | 不进入离职流程 |

### 2.1 权限代码

沿用现有权限：

| 权限代码 | 用途 |
|---|---|
| `employee:view` | 查看员工列表和脱敏档案 |
| `employee:sensitive:view` | 查看完整身份证号、银行卡号等敏感信息 |
| `employee:update` | 编辑权限范围内员工资料 |
| `employee:resign` | 一键办理员工离职 |
| `employee:create` | 新增员工 |
| `social:manage` | 雇主险增保管理 |
| `talent:menu` | 查看人才库菜单 |

### 2.2 驻厂数据范围

驻厂专员角色继续使用：

```text
role_code = onsite_staff
data_scope = 5（授权项目）
```

后端必须根据 `sys_user_project` 强制过滤：

```text
当前登录用户
  → sys_user_project.user_id
  → labor_project.id
  → labor_project.customer_id
  → hr_employee_job.project_id/customer_id
  → hr_employee.id
```

驻厂专员不得通过修改 `customerId`、`projectId`、`employeeId` 参数访问未授权数据。

## 3. 功能模块拆解

## 3.1 小程序底部菜单恢复与点击性能

### 3.1.1 菜单结构

恢复为五项固定菜单：

```text
工作台｜驻厂｜预支｜工资｜我的
```

“驻厂”进入页面后的页面标题仍显示“驻厂管理”。底部菜单使用短名称，避免五个字挤压和换行。

### 3.1.2 样式规则

- 恢复修改前的简洁白底菜单栏。
- 图标和文字垂直居中，五项等宽。
- 不使用点击瞬间背景色。
- 不使用 `:active` 缩放、透明度变化或渐变闪烁。
- 不使用 `hover-class="tab-pressed"`。
- 当前页面允许使用稳定的文字/图标选中态，但点击过程中不得再叠加临时颜色。
- 菜单文字统一为单行，字号不小于 `26rpx`。

### 3.1.3 延迟整改

点击菜单时只执行一次 `wx.switchTab`，不得先等待接口：

```javascript
switchTab(event) {
  const item = this.data.list[event.currentTarget.dataset.index];
  if (!item || item.pagePath === this.data.currentPath) return;
  wx.switchTab({ url: item.pagePath });
}
```

性能规则：

- 页面数据缓存有效期：20 秒。
- 页面未被标记为脏数据时，切回页面不重复请求。
- 保存员工、入职、离职、雇主险后再通过 `markDirty()` 标记相关页面刷新。
- 不在菜单点击中执行 `setData → 请求 → switchTab` 的串行链路。
- 防止同一菜单连续点击重复导航。
- 员工列表仅加载当前客户数据，禁止每次下载全公司员工后再前端过滤。

涉及文件：

```text
wechat-miniprogram/miniprogram/custom-tab-bar/index.js
wechat-miniprogram/miniprogram/custom-tab-bar/index.wxml
wechat-miniprogram/miniprogram/custom-tab-bar/index.wxss

```

## 3.3 工作台与驻厂管理关联

### 3.3.1 统一数据源

工作台和驻厂管理必须共用以下接口：

```text
GET /api/employees/onsite-overview
GET /api/employees?customerId={id}&employeeStatus={status}
GET /api/work-tasks?taskStatus=0
GET /api/work-tasks?taskStatus=1
```

禁止工作台和驻厂页分别使用不同口径统计同一状态。

### 3.3.2 工作台布局

工作台只保留三类现场信息：

1. 当前客户/项目概览。
2. 需要立即处理的人员事项。
3. 常用功能入口。

工作台快捷入口：

| 入口 | 点击结果 |
|---|---|
| 新增员工 | 打开新增员工页，并默认当前客户/项目 |
| 待到岗 | 进入驻厂页并筛选 `pending` |
| 在职员工 | 进入驻厂页并筛选 `active` |
| 一键离职 | 进入驻厂页并筛选 `active`，员工卡显示离职按钮 |
| 离职记录 | 进入驻厂页并筛选 `left` |

### 3.3.3 客户关联规则

- 工作台选择客户后，驻厂管理自动继承该客户。
- 驻厂管理切换客户后，返回工作台仍保留该客户。
- 客户统计、员工列表和待办列表必须同时变化。
- 只有一个授权客户时隐藏客户切换器。
- 无授权客户时显示“当前账号尚未分配客户项目”，不返回全公司数据。

## 3.4 身份证和银行卡信息展示

### 3.4.1 页面展示

员工详情增加“证件与账户信息”卡片：

| 字段 | 默认显示 | 完整显示条件 |
|---|---|---|
| 身份证号 | `320***********1234` | 拥有 `employee:sensitive:view`，并点击“查看完整信息” |
| 银行名称 | 完整显示 | 拥有员工查看权限 |
| 银行卡号 | `6222 **** **** 1234` | 拥有 `employee:sensitive:view`，并点击“查看完整信息” |
| 手机号 | `138****1234` | 敏感权限查看完整 |
| 身份证地址 | 默认显示“已填写” | 敏感权限查看完整 |

不得在花名册列表一次性返回完整身份证号和银行卡号。

### 3.4.2 查看流程

```text
进入员工详情
  → 默认请求脱敏数据
  → 点击“查看完整信息”
  → 二次确认“仅限业务办理使用”
  → 请求敏感详情接口
  → 后端校验企业、项目范围和敏感权限
  → 返回完整字段
  → 写入敏感访问日志
```

使用现有接口扩展：

```http
GET /api/employees/123?showSensitive=1&reason=驻厂员工资料核验
Authorization: Bearer <token>
```

成功响应示例：

```json
{
  "code": 0,
  "message": "ok",
  "data": {
    "basicInfo": {
      "id": 123,
      "name": "张三",
      "idCardNo": "320xxxxxxxxxxxxxxx",
      "bankName": "中国建设银行",
      "bankCardNo": "6222xxxxxxxxxxxx"
    }
  }
}
```

失败响应：

```json
{
  "code": 403,
  "message": "无敏感信息查看权限",
  "data": null
}
```

### 3.4.3 安全规则

- 服务端先执行 `employeeScope`，再判断敏感权限。
- 每次完整查看写入 `sys_sensitive_access_log`。
- 日志记录：企业、员工、操作人、字段类型、查看原因、IP、时间。
- 前端离开页面后清除完整敏感字段，不写入本地缓存。
- 禁止在 `console.log`、错误日志和审计日志中记录完整身份证号、银行卡号。
- 敏感信息查看接口使用 `sensitiveLimiter`。

## 3.5 在职与离职一键流转

### 3.5.1 员工卡操作

正常在职员工卡显示：

```text
查看详情｜编辑资料｜雇主险｜一键办理离职
```

点击“一键办理离职”打开单页确认，不再经过多个交接步骤。

### 3.5.2 离职页面字段

| 字段 | 必填 | 默认值/规则 |
|---|---:|---|
| 离职日期 | 是 | 默认当天，可修改 |
| 离职类型 | 是 | 主动离职、辞退、协商解除、合同到期 |
| 离职原因 | 否 | 快捷选项加自由备注；空白保存“未填写” |
| 工牌已归还 | 否 | 按实际情况勾选 |
| 工服/工具已归还 | 否 | 按实际情况勾选 |
| 宿舍已清退 | 否 | 按实际情况勾选 |
| 考勤已确认 | 否 | 按实际情况勾选 |
| 已减保 | 条件必填 | 当前雇主险保障中时必须勾选 |

### 3.5.3 一键办理事务

调用：

```http
POST /api/employees/123/resign
Content-Type: application/json
```

请求示例：

```json
{
  "leaveDate": "2026-08-12",
  "leaveType": 1,
  "leaveReason": "个人原因",
  "badgeReturned": 1,
  "toolsReturned": 0,
  "dormCleared": 0,
  "attendanceConfirmed": 1,
  "terminateEmployerInsurance": 1
}
```

同一数据库事务必须完成：

1. 校验员工属于当前企业和当前账号数据范围。
2. 校验员工当前为在职且未重复离职。
3. 新增 `hr_resignation` 离职记录。
4. 按实际勾选保存交接清单，不要求全部勾选。
5. 当前有雇主险时，校验“已减保”并更新雇主险状态。
6. 更新 `hr_employee.employee_status = 3`。
7. 更新 `hr_employee.lifecycle_status = 'LEFT'`。
8. 结束当前 `hr_employee_job`，保留历史任职记录。
9. 停用关联员工账号并增加 `token_version`，旧 Token 立即失效。
10. 通过 `employee_id` 幂等写入或更新 `talent_candidate`。
11. 关闭离职、减保相关待办。
12. 写入操作日志和业务通知。

成功响应：

```json
{
  "code": 0,
  "message": "离职办理成功",
  "data": {
    "employeeId": 123,
    "resignationId": 45,
    "completed": true,
    "talentFlowed": true
  }
}
```

### 3.5.4 人才库回流

离职办结后人才库保留：

```text
姓名、手机号、身份证摘要、原客户、原项目、原岗位、入职日期、
离职日期、离职类型、离职原因、招聘渠道、用工模式、费用模式、
原员工ID、人才来源=离职回流、可用状态、负责人、创建/更新时间
```

同一员工多次入离职不得生成重复人才：

```text
优先唯一键：company_id + source_employee_id
兼容查重：company_id + id_card_hash
```

驻厂专员查看人才库时，仍只能看到其授权项目产生的离职回流人员。

## 3.6 网页端花名册只显示在职员工

### 3.6.1 在职口径

网页端“员工花名册”固定条件：

```sql
e.employee_status = 2
AND e.lifecycle_status <> 'OFFBOARDING'
AND e.deleted_at IS NULL
AND j.job_status = 1
```

面试、待到岗、未入职、离职办理和已离职员工不出现在网页花名册。

这些人员分别进入：

| 人员状态 | 查询入口 |
|---|---|
| 面试、未入职 | 人才库 |
| 待到岗 | 驻厂工作台/入职待办 |
| 离职办理 | 离职待办 |
| 已离职 | 人才库/员工历史档案 |

### 3.6.2 服务端过滤

新增明确视图参数，避免只在网页前端过滤：

```http
GET /api/employees?view=activeRoster&page=1&pageSize=50
```

后端规则：

```javascript
if (query.view === 'activeRoster') {
  where.push('e.employee_status = 2');
  where.push("e.lifecycle_status <> 'OFFBOARDING'");
  where.push('j.job_status = 1');
}
```

网页端花名册、导出和客户分组统计统一传递 `view=activeRoster`。

导出接口同样只允许导出当前在职花名册：

```text
GET /api/export/employees.xlsx?view=activeRoster
```

## 3.7 驻厂端数据隔离

### 3.7.1 员工列表

驻厂端员工查询必须满足：

```sql
e.company_id = :companyId
AND EXISTS (
  SELECT 1
  FROM sys_user_project up
  WHERE up.user_id = :currentUserId
    AND up.project_id = j.project_id
)
```

新录入但尚未分配项目的面试人员，仅创建人本人可见；正式分配项目后改用项目授权范围。

### 3.7.2 客户列表

驻厂端客户下拉列表不得从全公司客户表直接返回，应由授权项目反查：

```sql
SELECT DISTINCT c.id, c.customer_name
FROM sys_user_project up
JOIN labor_project p ON p.id = up.project_id
JOIN crm_customer c ON c.id = p.customer_id
WHERE up.user_id = :currentUserId
  AND p.company_id = :companyId;
```

### 3.7.3 详情、编辑、离职和敏感查看

以下接口必须重复执行相同数据范围校验：

```text
GET  /api/employees/:id
PUT  /api/employees/:id
POST /api/employees/:id/onboard
POST /api/employees/:id/resign
PUT  /api/employees/:id/social-security
GET  /api/employees/:id?showSensitive=1
```

不能认为“列表看不到”就足够安全，直接输入其他员工 ID 也必须返回 `404` 或 `403`。

## 4. 数据结构

本轮原则上复用现有表，不新增重复员工表。

### 4.1 核心表关系

| 表 | 主键 | 本轮用途 |
|---|---|---|
| `hr_employee` | `id BIGINT` | 员工主档、在职/离职状态、加密身份证和银行卡信息 |
| `hr_employee_job` | `id BIGINT` | 当前及历史客户、项目、岗位任职记录 |
| `hr_resignation` | `id BIGINT` | 离职日期、类型、原因和交接勾选记录 |
| `talent_candidate` | `id BIGINT` | 面试、未入职和离职人员回流 |
| `sys_user_project` | 联合关系 | 驻厂专员项目授权 |
| `sys_sensitive_access_log` | `id BIGINT` | 身份证、银行卡完整查看留痕 |
| `hr_operation_log` | `id BIGINT` | 一键离职等业务操作审计 |

### 4.2 建议补充索引

上线前检查并补齐：

```sql
CREATE INDEX idx_employee_company_status
  ON hr_employee(company_id, employee_status, lifecycle_status, deleted_at);

CREATE INDEX idx_job_company_project_status
  ON hr_employee_job(company_id, project_id, job_status, employee_id);

CREATE INDEX idx_user_project_user_project
  ON sys_user_project(user_id, project_id);

CREATE INDEX idx_talent_company_employee
  ON talent_candidate(company_id, source_employee_id);
```

若索引已存在，迁移脚本必须幂等跳过。

## 7. REST 接口设计

| 方法 | URL | 权限 | 说明 |
|---|---|---|---|
| GET | `/api/employees/onsite-overview` | `employee:view` | 当前授权范围驻厂统计 |
| GET | `/api/employees?view=activeRoster` | `employee:view` | 网页端正常在职花名册 |
| GET | `/api/employees?customerId=:id&employeeStatus=:status` | `employee:view` | 驻厂当前客户员工 |
| GET | `/api/employees/:id` | `employee:view` | 脱敏员工详情 |
| GET | `/api/employees/:id?showSensitive=1&reason=:reason` | `employee:sensitive:view` | 完整敏感信息并留痕 |
| POST | `/api/employees/:id/resign` | `employee:resign` | 一键办理离职 |
| GET | `/api/talents?sourceType=RESIGNED` | `talent:menu` | 离职回流人才 |
| GET | `/api/export/employees.xlsx?view=activeRoster` | `employee:export` | 导出正常在职花名册 |

统一错误响应：

```json
{
  "code": 403,
  "message": "无权访问该客户或员工数据",
  "data": null
}
```

## 8. 权限与风控逻辑

### 8.1 必须满足

- 企业之间使用 `company_id` 强制隔离。
- 驻厂账号使用授权项目强制隔离。
- 完整身份证号、银行卡号只在单员工详情按需返回。
- 敏感查看、离职、导出必须写审计日志。
- 离职后员工账号立即失效。
- 离职操作必须二次确认。
- 导出只包含操作者权限范围内的正常在职员工。
- 人才库离职回流记录不得突破原项目数据范围。

### 8.2 禁止行为

- 禁止列表接口返回全量身份证、银行卡明文。
- 禁止前端传入 `companyId` 决定企业范围。
- 禁止驻厂端先获取全公司数据再前端过滤。
- 禁止删除离职员工主档和历史任职记录。
- 禁止在日志记录完整密码、身份证号、银行卡号和 Token。
