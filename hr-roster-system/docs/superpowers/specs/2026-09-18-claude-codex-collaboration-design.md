# Claude 与 Codex 安全协作设计

日期：2026-09-18
适用项目：`/Users/zhuhao/Documents/moluo/hr-roster-system`

## 1. 目标

建立 Claude 与 Codex 可长期执行的协作机制，确保双方：

- 不在同一个物理目录或同一个开发分支并行修改；
- 不覆盖对方未提交改动；
- 通过明确提交交接，不通过复制文件交接；
- 将本地修改、提交、审核、远程同步和生产发布分别记录；
- 对数据库、敏感信息和生产部署保持单一责任人与确认门禁。

## 2. 推荐架构

采用“独立 Worktree + 独立分支 + 集成目录 + 单一发布人”模式。

| 角色 | 建议目录 | 分支前缀 | 默认职责 |
|---|---|---|---|
| 集成与发布 | `/Users/zhuhao/Documents/moluo/hr-roster-system` | `integration/` | 合并、全量验证、发布 |
| Claude | `/Users/zhuhao/CodexWorktrees/hr-roster-claude` | `claude/` | 独立任务开发或审核 |
| Codex | `/Users/zhuhao/CodexWorktrees/hr-roster-codex` | `codex/` | 独立任务开发或审核 |

集成目录不用于双方同时开发。一个任务只能有一个主开发者；另一方默认只读审核。

## 3. 任务生命周期

每项任务按以下状态流转：

```text
待分配 → 开发中 → 已提交 → 待审核 → 审核通过 → 已集成
       → 全量验证通过 → 待发布确认 → 已部署 → 线上验收通过
```

状态不能合并表述。例如“本地测试通过”不能写成“已经上线”，“已提交”不能写成“已推送”。

### 3.1 开始任务

任务发起人必须提供：

- 任务名称；
- 基础提交号；
- 工作目录和分支；
- 允许修改和禁止修改的范围；
- 数据库影响；
- 是否允许提交、推送、部署或上传小程序；
- 完成标准。

主开发者开始前运行只读检查：

```bash
pwd
git branch --show-current
git rev-parse --short HEAD
git status --short
```

发现目录、分支或基础提交不一致时停止开发，不自行覆盖或重置。

### 3.2 开发与提交

- 一个分支只承载一个明确任务。
- 先写失败测试，再做最小实现。
- 使用显式文件列表执行 `git add`，禁止默认使用 `git add .`。
- 提交前运行专项测试、`npm run check` 和 `git diff --check`。
- 提交信息使用 Conventional Commits。
- 提交说明列出功能范围、测试证据和已知限制。

### 3.3 审核与修改

- Claude 开发时，由 Codex 默认执行只读审核；Codex 开发时，Claude 可执行交叉审核。
- 审核者先检查提交差异、测试证据、数据库和发布影响。
- 审核者不直接修改开发者分支；发现问题后由原开发者优先修正。
- 如需审核者代为修复，必须由用户明确授权并使用新的独立提交。

### 3.4 集成

- 集成人只接收明确提交号，不接收散落文件。
- 优先使用 `git cherry-pick <commit>`，便于追踪任务边界。
- 冲突由集成人处理；不能通过覆盖整个文件解决。
- 集成后重新运行专项测试和 `npm run check`。

## 4. 文件占用规则

以下高冲突文件同一时间只能由一个任务占用：

- `public/app.js`
- `public/index.html`
- `public/styles.css`
- `src/services/operations.service.js`
- `package.json`
- `sql/schema.mysql.sql`
- `scripts/build-release-package.sh`
- `scripts/verify-release-package.sh`
- `scripts/deploy-production.sh`
- 微信小程序全局配置与公共请求模块

任务交接单必须声明这些文件的占用情况。第二个任务需要相同文件时，应等待第一个任务提交并重新基于最新集成提交开始。

## 5. 数据库安全

- 数据库需求由一个主开发者负责完整迁移。
- 迁移文件使用唯一日期和任务名，创建前先检查现有文件名。
- 已进入生产的迁移文件禁止修改；后续修复新增迁移。
- 迁移必须幂等，禁止 `DROP`、`TRUNCATE` 和无条件删除业务数据。
- SQL 必须参数化；敏感数据不得写入测试日志和协作说明。
- 生产迁移必须经过代码、数据库、附件备份和发布包安全检查。
- 生产验收只执行只读检查，不创建测试员工、工资或考勤记录。

## 6. 密钥与生产权限

### 6.1 默认权限

Claude 和 Codex均可：

- 在各自 Worktree 开发；
- 运行本地测试；
- 在获得授权后创建本地提交；
- 执行不修改外部状态的审核。

未经用户明确确认，双方均不得：

- 推送远程分支；
- 修改 Git 全局配置；
- SSH 登录生产服务器；
- 修改生产数据库；
- 部署 Web/API；
- 上传、提交审核或发布微信小程序；
- 操作短信、公众号或其他真实通知渠道。

### 6.2 单一发布人

每次发布只指定一个发布人。当前建议 Codex 作为 Web/API 发布人，沿用已经验证的发布包、备份和只读验收流程。Claude 可以复核发布提交和测试证据，但不得对同一版本重复部署。

发布人必须记录：

- 集成提交号；
- 发布包路径和 SHA-256；
- 代码、数据库和附件备份；
- 数据库迁移结果；
- 容器健康状态；
- 公网健康、权限拦截和只读 smoke 结果；
- 小程序是否属于本次发布范围。

## 7. 冲突和事故处理

### 7.1 发现并行修改

1. 双方立即停止继续编辑。
2. 分别记录目录、分支、HEAD 和 `git status --short`。
3. 不执行 `git reset --hard`、`git checkout --` 或批量清理。
4. 各自提交可独立保存的改动，或生成只读差异供集成人审核。
5. 由一位集成人逐个提交合并并重新测试。

### 7.2 生产异常

1. 停止后续部署与小程序发布。
2. 保留日志、发布包、提交号和故障时间。
3. 检查应用与数据库容器健康状态。
4. 优先使用上线前代码备份回滚应用。
5. 数据库恢复属于高风险操作，必须再次获得用户明确确认。
6. 回滚后重新执行公网和只读 smoke 验收。

## 10. 落地范围

设计确认后的实施工作包括：

1. 在 `AGENTS.md` 增加双代理协作硬性规则。
2. 新建可复制的任务交接模板。
3. 新建只读协作检查脚本，输出目录、分支、HEAD、工作区状态和高冲突文件占用提示。
4. 为协作检查脚本增加契约测试。
5. 验证脚本不读取或输出 `.env`、Token、身份证、手机号和工资数据。

不包含自动合并、自动推送、自动部署或自动清理工作区。
